# M5-12详细设计：Nuxt自动导入与隐式依赖边界

这份设计文档说明 `M5-12` 为什么选择 Nuxt 自动导入与隐式依赖场景，以及它将如何接入现有方法库。

## 设计目标

把 Nuxt 自动导入问题从“怎么省掉 import”还原成“默认框架能力、应用公共入口、feature 内部实现与环境前提如何分层”的边界设计问题，并用一篇案例把大型 Nuxt 项目里更稳的依赖组织方式说清楚。

## 为什么在 M5-12 选 Nuxt自动导入与隐式依赖

在当前方法库里，已经补齐了：

- 页面型案例
- 基础组件型案例
- SSR / hydration 运行时边界
- Nuxt 页面数据获取与渲染边界
- 状态管理型案例
- 复杂交互型案例
- 认证与权限型案例
- 路由与布局型案例
- 容错与降级型案例
- 异步加载型案例
- Nuxt 运行时边界型案例
- Nuxt 响应策略型案例
- Nuxt 执行时机型案例

下一步最自然补的，就是 Nuxt 自动导入与隐式依赖边界这条横向主线。因为它会同时影响：

- composable 与工具函数的公共暴露面
- 页面顶层代码的依赖可读性
- `imports.dirs` 的扩张方式与目录边界
- server-only、client-only 和双端共享能力的组织方式

所以 Nuxt 自动导入与隐式依赖是一个非常适合作为 `M5-12` 的横向扩展线。

## 本轮案例的复杂度中心

本轮复杂度中心主要有四个：

- 默认框架能力、应用公共入口、feature 内部实现的三层依赖模型
- 自动导入便利性与隐式依赖可读性的平衡
- `imports.dirs` 的筛选边界与目录治理策略
- server-only / client-only / 双端共享能力的环境边界设计

## 与现有框架的映射关系

本轮将重点强化统一框架中的这些步骤：

- 第二步：找到真正的复杂度中心
- 第三步：先拆数据，再拆视图
- 第六步：显式数据流优先，隐式通信后退
- 第七步：先设计扩展点，再谈复用
- 第九步：让页面消费层尽量薄
