# M5-13详细设计：Nuxt Server Routes与BFF接口边界

这份设计文档说明 `M5-13` 为什么选择 Nuxt Server Routes 与 BFF 接口场景，以及它将如何接入现有方法库。

## 设计目标

把 Nuxt Server Routes 问题从“接口放到 `server/api` 就行”还原成“页面契约、BFF 聚合、请求上下文和下游适配如何分层”的边界设计问题，并用一篇案例把大型 Nuxt 项目里更稳的接口组织方式说清楚。

## 为什么在 M5-13 选 Nuxt Server Routes与BFF接口边界

在当前方法库里，已经补齐了：

- 页面型案例
- 基础组件型案例
- SSR / hydration 运行时边界
- Nuxt 页面数据获取与渲染边界
- 状态管理型案例
- 复杂交互型案例
- 认证与权限型案例
- 路由与布局型案例
- 容错与降级型案例
- 异步加载型案例
- Nuxt 运行时边界型案例
- Nuxt 响应策略型案例
- Nuxt 执行时机型案例
- Nuxt 依赖边界型案例

下一步最自然补的，就是 Nuxt Server Routes 与 BFF 接口边界这条横向主线。因为它会同时影响：

- 页面数据契约如何从下游接口中解耦
- `server/api` 如何成为前端级接口层，而不是原样透传层
- 请求级上下文准备与接口级业务编排如何分工
- 页面数据获取链路与服务端组装语义如何协同

所以 Nuxt Server Routes 与 BFF 接口边界是一个非常适合作为 `M5-13` 的横向扩展线。

## 本轮案例的复杂度中心

本轮复杂度中心主要有四个：

- 页面消费层、BFF 接口层、服务组装层和下游适配层的四层接口模型
- 页面契约与 provider 原始结构的解耦
- 请求上下文准备与接口级业务组装的责任边界
- 页面数据获取语义与服务端契约输出语义的协同设计

## 与现有框架的映射关系

本轮将重点强化统一框架中的这些步骤：

- 第二步：找到真正的复杂度中心
- 第三步：先拆数据，再拆视图
- 第六步：显式数据流优先，隐式通信后退
- 第八步：把副作用从组件和页面里收出去
- 第九步：让页面消费层尽量薄
