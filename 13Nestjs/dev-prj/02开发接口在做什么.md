
**一、开发一个接口，先做什么？**

这里以登录注册为例

| 顺序 | 思考的问题 | 当前项目中的对应实现 |
| --- | --- | --- |
| 1. 明确用例 | 谁能调用？输入什么？成功、失败分别是什么？ | 超管创建账号；用户用邮箱、密码登录 |
| 2. 设计数据库 | 保存什么？哪些规则必须始终成立？ | 邮箱唯一、密码只存哈希、用户关联角色 |
| 3. 定义 DTO | 请求允许哪些字段？格式与默认值是什么？ | Zod schema 校验，推导 `CreateUserDto`、`LoginDto` |
| 4. 编写 Service | 完成业务需要哪些步骤？ | 创建：查角色、哈希、入库；登录：查用户、验密、签发 token |
| 5. 接入 Controller、Guard | 路由是什么？谁有资格执行？ | Controller 接请求，Guard 认证与授权 |
| 6. 装配 Module | Nest 如何找到类、注入依赖？ | 注册 Controller、Service，导入业务模块 |
| 7. 统一出口 | 成功和异常如何返回？ | Interceptor 包装成功，Filter 处理异常 |

这也是我们以后开发其他模块时可以重复使用的顺序。

**二、创建用户：`POST /api/user`**

先看 [数据库模型](/Users/fri/Desktop/personal/my-resume-fullstack/apps/api/prisma/schema.prisma:64)。

`User` 保存邮箱、昵称、密码哈希等资料；`Role` 保存角色；`UserRole` 保存“哪个用户拥有哪些角色”。因此创建用户时，需要同时保存用户记录和角色关联。

然后看 [创建输入 schema](/Users/fri/Desktop/personal/my-resume-fullstack/apps/api/src/user/dto/user.schema.ts:20)。它负责：

- 邮箱必填，去首尾空格、转小写、检查格式。
- 密码检查长度，保持原样。
- 昵称、头像可选；`roleKey` 默认 `user`。
- 拒绝请求指定 `id`、`passwordHash` 等内部字段。

**DTO 校验解决“输入是否合法”；数据库约束解决“最终数据是否允许写入”。** 例如邮箱格式合法，并不代表邮箱没有被占用。

实际请求按下面的顺序执行：

```text
验证 token，恢复操作者身份
  → 检查操作者的超管角色与创建权限
  → 校验、规范化请求输入
  → Controller 委托 Service
  → Service 完成创建
  → 统一包装响应
```

[UserCreationGuard](/Users/fri/Desktop/personal/my-resume-fullstack/apps/api/src/user/user-creation.guard.ts:17) 判断调用资格；[Controller](/Users/fri/Desktop/personal/my-resume-fullstack/apps/api/src/user/user.controller.ts:44) 声明路由和输入，没有承担数据库业务。

核心在 [UserService.create](/Users/fri/Desktop/personal/my-resume-fullstack/apps/api/src/user/user.service.ts:42)：

```text
查找要分配的角色
  → 不存在则抛业务异常
  → 对密码生成哈希
  → 创建用户，同时创建 UserRole
  → 返回允许公开的字段
```

这里有三个值得理解的点：

1. **`roles.create` 是 Prisma 的关联写入。** 用户与角色关联一起成功；关联失败，用户写入也回滚。
2. **当前没有预查询邮箱是否重复。** 数据库唯一约束保障并发安全；冲突由全局 Filter 返回 409，Service 不重复捕获 Prisma 错误。
3. **`select` 从源头排除密码哈希。** `create` 本身就返回选中的创建结果，无须再查一次，也无须先查出密码再删除。

数据库连接则由现成的 [PrismaService](/Users/fri/Desktop/personal/my-resume-fullstack/apps/api/src/prisma/prisma.service.ts:28) 管理，业务 Service 通过依赖注入使用它。

**三、登录：`POST /api/auth/login`**

登录的职责是**验证身份并签发凭证**，因此放在 `auth` 模块。

[LoginDto](/Users/fri/Desktop/personal/my-resume-fullstack/apps/api/src/auth/dto/login.schema.ts:11) 只接收邮箱和密码。邮箱与创建时采用相同的规范化规则，密码仍保持原样。

[登录 Controller](/Users/fri/Desktop/personal/my-resume-fullstack/apps/api/src/auth/auth.controller.ts:27) 的两个关键点：

- `@Public()`：尚未登录的人也能访问登录接口。
- `@HttpCode(200)`：登录成功返回 200；创建用户默认返回 201。

[AuthService.login](/Users/fri/Desktop/personal/my-resume-fullstack/apps/api/src/auth/auth.service.ts:46) 完成：

```text
按邮箱查询未删除用户、密码哈希、角色和权限
  → 用户不存在或验密失败：统一返回“账号或密码不正确”
  → 组装安全的用户身份
  → 签发 JWT
  → 返回 token、用户信息、角色和权限
```

密码校验不能写成：

```ts
hashPassword(loginDto.password) === user.passwordHash
```

因为创建哈希时会生成**随机盐**。登录应使用 [verifyPassword](/Users/fri/Desktop/personal/my-resume-fullstack/apps/api/src/common/password.ts:73)，读取数据库哈希中的原盐和参数，重新计算后比较。

[JWT 签发](/Users/fri/Desktop/personal/my-resume-fullstack/apps/api/src/auth/auth.service.ts:76) 使用用户的稳定 `id` 作为 `sub`。JWT 是签名而非加密，所以载荷没有放密码，也没有放角色、权限快照。

后续请求携带：

```http
Authorization: Bearer <token>
```

全局 Guard 验签，再通过 `sub` 查询数据库当前身份。这样角色调整或软删除会在下一次请求生效，代价是每次受保护请求都有一次身份查询。

**四、第一个超管为什么要通过 seed 创建？**

创建接口要求先登录超管，但空数据库还没有超管，所以需要一个初始化入口。

我已调整 [seed.ts](/Users/fri/Desktop/personal/my-resume-fullstack/apps/api/prisma/seed.ts:62)，准备以下本地学习账号：

| 项目 | 值 |
| --- | --- |
| 登录邮箱 | `super@example.com` |
| 昵称 | `super` |
| 初始学习密码 | `Super123!` |
| 角色 | `super_admin` |

`super` 是昵称，登录使用邮箱。seed 会初始化角色和权限，并在事务中创建账号、关联超管角色；重复执行不重置已有密码，不自动恢复软删除账号，旧 `admin` 账号保留。

数据库准备好后，由你执行：

```bash
pnpm --filter @template/api exec prisma migrate deploy
pnpm --filter @template/api exec prisma generate
pnpm --filter @template/api exec prisma db seed
```

三条命令分别负责：**改数据库结构、生成查询 Client 与类型、写入初始化数据**。如果是旧库，需要先为旧账号补齐唯一邮箱，再执行最新迁移；具体步骤和 Apifox 请求已同步到 [学习文档](/Users/fri/Desktop/personal/my-resume-fullstack/docs/server/04_账号创建与登录_业务讨论.md:127)。

接下来你可以按“超管登录 → 创建学习用户 → 学习用户登录”串起来，并对照代码看：**每一步是在检查输入、判断权限、执行业务，还是保证数据一致性。** 这样各层为什么存在，就会逐渐具体起来。
