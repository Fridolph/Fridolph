# NestJS 应用生命周期

> 应用生命周期关注服务如何启动、运行和关闭；[请求生命周期](./q_nestjs_7-request_lifecycle)关注一次请求如何被处理。

## 1. NestJS 应用从启动到关闭的完整生命周期是什么？

::: details 参考回答

NestJS 应用的生命周期，可以分成创建、初始化、运行和关闭四个阶段。

启动时，先在 `main.ts` 中调用 `NestFactory.create(AppModule)`，扫描模块、解析依赖并创建实例，再配置全局管道、拦截器等。

调用 `app.init()` 或 `app.listen()` 后，会先执行 `onModuleInit`，再执行 `onApplicationBootstrap`。如果调用的是 `listen()`，初始化完成后就开始监听端口、处理请求。

关闭时，可以主动调用 `app.close()`，也可以启用关闭钩子后接收系统关闭信号。顺序是 `onModuleDestroy`、`beforeApplicationShutdown`，然后关闭应用连接，最后执行 `onApplicationShutdown`。

这些钩子主要用来初始化和释放资源，异步钩子也会被等待。不过，完整的优雅停机，还要处理正在执行的请求、后台任务和数据库连接，不能只靠生命周期钩子。

如果有数据库，我会先停止接收新工作，等正在执行的请求和事务在限定时间内结束，再关闭连接池。这里关闭的是应用到数据库的连接，不是关闭 PostgreSQL 服务。数据库突然断连属于运行时故障，不会自动触发这些关闭钩子，需要另外处理超时、恢复连接，以及写操作重试时的幂等问题。

:::

**回答节奏**：先讲四个阶段，再按顺序说出五个钩子，控制在一到两分钟。涉及数据库时补充最后一段，整体控制在三分钟内。

**追问入口**：`app.init()` 和 `app.listen()` 有什么区别？怎样让应用收到 `SIGTERM` 后执行清理？数据库断线时，正在执行的事务一定会回滚吗？

## 完整流程

```text
执行入口文件 main.ts
    ↓
NestFactory.create(AppModule)
    ↓
扫描模块、解析依赖关系
创建 Provider、Controller 等实例
    ↓
配置应用
例如：全局 Pipe、Interceptor、CORS、关闭信号监听
    ↓
调用 app.init() 或 app.listen()
    ↓
onModuleInit()
    ↓
onApplicationBootstrap()
    ↓
开始监听端口（调用 listen 时）
    ↓
应用运行，处理请求
    ↓
触发正常关闭
例如：app.close()，或启用关闭钩子后收到 SIGTERM
    ↓
onModuleDestroy()
    ↓
beforeApplicationShutdown()
    ↓
关闭应用连接，例如 HTTP 服务
    ↓
onApplicationShutdown()
    ↓
应用关闭完成
```

**`NestFactory.create()` 会创建应用和依赖实例，但初始化生命周期钩子由后续的 `app.init()` 或 `app.listen()` 触发。** `app.init()` 只初始化应用；`app.listen()` 会在需要时完成初始化，并开始监听端口。

## 五个关键钩子

| 钩子 | 触发时机 | 常见用途 |
| --- | --- | --- |
| `onModuleInit()` | 所在模块的依赖解析完成后，在应用初始化期间调用 | 初始化组件、建立数据库连接 |
| `onApplicationBootstrap()` | 所有模块初始化完成后、开始监听前 | 依赖整个应用完成初始化的启动工作 |
| `onModuleDestroy()` | 关闭流程开始时 | 停止组件工作、清理资源 |
| `beforeApplicationShutdown()` | 所有 `onModuleDestroy()` 完成后，关闭应用连接前 | 关闭前的协调和清理 |
| `onApplicationShutdown()` | 应用连接关闭后 | 最后的清理工作 |

这描述的是阶段顺序，不代表不同模块、Provider 之间存在任意可依赖的固定调用顺序；初始化依赖应通过明确的依赖关系或协调逻辑表达。

## 关键细节

### 异步钩子会被等待

钩子返回 Promise 时，Nest 会等待其完成。因此，关键初始化失败，可以阻止应用正常启动；关闭钩子也应避免无限等待。

### 系统关闭信号需要显式启用

```ts
import { NestFactory } from '@nestjs/core'
import { AppModule } from './app.module'

async function bootstrap() {
  const app = await NestFactory.create(AppModule)

  app.enableShutdownHooks()

  await app.listen(3000)
}

bootstrap()
```

`app.close()` 可以主动触发关闭流程，不要求先调用 `enableShutdownHooks()`；`enableShutdownHooks()` 用于监听运行环境支持的系统关闭信号，例如 `SIGTERM`。

### 关闭钩子不等于完整的优雅停机

数据库客户端、定时任务、消息消费者和后台任务，仍需按业务情况协调关闭。应考虑停止接收新工作、等待进行中的工作完成，再释放其依赖的资源，避免先断开数据库导致请求失败。

`SIGKILL` 等强制终止不会给应用执行清理钩子的机会。`app.close()` 也不等于退出 Node.js 进程，未清理的定时器或后台任务仍可能让进程继续运行。

**请求作用域的 Provider 不参与这些应用生命周期钩子**，因为它们的生命周期并不绑定到整个应用。

## 有数据库时，应用如何安全下线？

**应用下线通常只关闭自己持有的数据库连接池，不关闭 PostgreSQL 服务。** 数据库可能同时服务其他应用或其他实例；一个 NestJS 实例下线，不应影响它们。

### 正常下线：先排空工作，再断开数据库

```text
收到 SIGTERM，或主动开始下线
    ↓
标记应用正在下线，让就绪检查不再通过
配合负载均衡摘流，拒绝新的业务工作
    ↓
停止领取消息、启动新定时任务等后台工作
    ↓
在限定时间内，等待已有请求和后台任务完成
事务正常完成时提交，失败时回滚
    ↓
确认不再有工作使用数据库
    ↓
关闭数据库客户端或连接池
    ↓
完成剩余清理，进程退出
```

这是需要应用和部署环境共同实现的业务顺序，**不是调用 `enableShutdownHooks()` 就会自动完成的流程**。摘流可能存在传播延迟，应用也应有下线状态检查，避免继续接收新业务；具体关闭 HTTP 连接和等待请求的行为，还要结合 HTTP 适配器及版本验证。

连接管理上，长时间运行的 NestJS 服务通常复用默认单例 Provider 中的 Prisma Client 或连接池，**不要每个请求都创建客户端、再调用 `$disconnect()`**，否则会造成连接反复建立和关闭。

### 数据库连接放在哪个钩子里关闭？

对自行管理的 Prisma Client，一种常见安排是：

- 在前面的关闭阶段设置下线状态、停止后台任务，并等待它们退出。
- HTTP 服务关闭、已有请求和后台任务均已处理后，在 `onApplicationShutdown()` 中 `await prisma.$disconnect()`，释放连接池。

**关键是关闭数据库前，使用它的工作已经结束，不能只看钩子名字。** 不要在 `onModuleDestroy()` 中不加协调地断开数据库，因为这时 HTTP 服务可能还未关闭，已有请求仍可能访问数据库。同样，若其他 Provider 的后续清理也需要数据库，就必须通过明确的协调逻辑保证它们先完成，不能依赖同一阶段各个钩子的偶然顺序。

若使用的 ORM 集成已经负责释放连接，应先确认它的关闭行为，避免与自定义逻辑冲突。关闭连接池不等于“替业务自动完成所有事务”，事务应由对应的业务逻辑提交或回滚。

### 等待和清理都要有时间上限

为请求、查询、事务和停机等待设置合理超时，并给部署平台留出足够的终止宽限时间。超过期限时，应记录未完成工作，按业务能力取消或中止，而不是一直等待。

仅用 `Promise.race()` 限时等待，并不会取消底层查询或任务；真正的中止能力取决于驱动、数据库超时设置和任务实现。不要一收到信号就调用 `process.exit()`，否则异步清理可能来不及完成。

## 突然掉线或被强制终止，数据库会怎样？

| 情况 | 是否执行应用关闭钩子 | 处理重点 |
| --- | --- | --- |
| 应用正常下线 | 主动 `app.close()`，或启用关闭钩子后收到支持的信号时执行 | 摘流、排空工作、关闭连接池 |
| 数据库重启、网络中断 | 不会仅因断连自动执行 | 查询超时与错误处理、连接恢复、有限重试 |
| 应用崩溃、断电或被 `SIGKILL` | 无法保证执行，`SIGKILL` 不会执行 | 数据库检测断连后清理会话；重启后核对未完成业务 |

### 数据库断连：先处理失败，再考虑恢复

当前查询或事务可能报错，也可能直到超时才发现连接不可用。应用应记录错误，对依赖数据库且暂时无法处理的请求返回适当的失败响应，例如 503；故障持续时，可将就绪检查标记为失败，避免持续承接无法完成的请求。

连接恢复方式取决于 Prisma、驱动或连接池的版本和配置，不能承诺所有查询都会自动重连并重试成功。通常让连接池淘汰失效连接、按需建立新连接；确实需要业务重试时，应设置次数上限、退避和抖动，避免故障期间大量实例同时重试。

**不要捕获到任意数据库错误就销毁并重建整个连接池。** 这可能影响其他正在执行的请求；先区分连接故障、约束冲突等错误，只对适合恢复的临时故障采取重试。

### 会话结束：未提交事务会回滚，但不能据此盲目重试写入

PostgreSQL 检测到连接结束并终止会话时，会回滚仍然打开、尚未提交的事务，并释放相关事务锁。网络中断不一定会被立即检测到，清理可能受到 TCP 检测及数据库超时设置的影响。

需要区分两个情况：

- **事务仍未提交**：会话结束时由数据库回滚，重连也不能继续原来的事务。
- **提交已发生，但响应没收到**：应用看到超时或断线，数据库里的修改却可能已经提交；自动提交的写操作也可能在数据库察觉断连前完成。

所以，**“没收到成功响应”不等于“写入没有成功”**。涉及保存、扣减等操作，应结合幂等键、唯一约束或版本条件更新，在必要时查询结果后再决定是否重试，避免重复写入。

应用进程被强制终止时，操作系统通常会回收它的套接字，数据库再按上述规则清理会话；不应把这个兜底机制当作正常停机方案。应用停机也不会自动回滚此前已经提交的业务数据。

## 学习场景：NestJS + Prisma + PostgreSQL

假设后续实现一个“保存学习笔记”的后端服务：

- 启动时：可以在初始化钩子中调用 Prisma 的 `$connect()`，提前确认数据库连接可用。
- 运行时：处理笔记读取、保存等请求。
- 正常下线时：停止接收新的保存请求和后台任务，等待已接收的工作在限定时间内完成，再调用 `$disconnect()` 释放连接池。
- 突然断线时：记录失败并处理超时；如果保存结果不确定，利用笔记 ID、请求幂等键或版本号核对结果，再决定是否重试。

显式调用 `$connect()` 是一种初始化选择；Prisma 也可以在第一次查询时建立连接，并非必须依靠该钩子。

## 记忆主线

**创建依赖 → 初始化 → 监听运行 → 关闭清理。**

**数据库关闭顺序：停止新工作 → 等待已有工作 → 关闭连接池。断线后先判断结果，写操作不能盲目重试。**
