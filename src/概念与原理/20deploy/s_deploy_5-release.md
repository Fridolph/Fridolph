# 发布、验证与回滚

## 交付的是版本，不是一个目录

可重复的发布需要固定源码提交、运行时版本和依赖锁文件。构建产物与版本关联，测试环境和生产环境使用同一份已验证产物，再注入各自配置。不要在服务器随手改文件后忘记回仓库。

```text
源码版本 → 锁定依赖 → 检查与测试 → 构建产物
         → 部署候选版本 → 就绪检查 → 切换流量
         → 验证指标 → 保留旧版本 / 回滚
```

本项目是静态文档站：开发在 dev，发布以 main 为入口，由现有 GitHub Actions 构建 Pages。学习笔记新增内容不需要引入新的发布服务。后端应用还需管理进程、迁移、配置和依赖服务，不能直接套用静态站方案。

## 发布前回答四个问题

1. **发布什么？** 提交号、产物校验、依赖和运行时版本可追踪。
2. **如何证明可用？** lint / 类型 / 单元测试之外，还要验证入口、静态资源、关键接口、鉴权和数据库访问。
3. **怎样观察异常？** 错误率、延迟分位数、数据库连接、资源占用，配合 requestId 和版本号串联日志。
4. **怎样回退？** 旧产物仍可取、旧版本兼容当前配置与数据库，明确执行人及触发条件。

## 数据库变更与代码发布

回滚代码不会撤销已写入的数据。优先使用 expand-contract：先增加兼容字段 / 接口，发布兼容读写版本，完成回填与验证，最后另一个窗口删除旧结构。耗时 DDL、索引构建和长事务要单独评估锁与超时。

PostgreSQL 的部分 DDL 可事务回滚，不等于所有迁移都低风险；`CREATE INDEX CONCURRENTLY` 等操作还有事务块限制。备份也需要经过恢复演练，确认恢复时间和可接受的数据丢失窗口。

## 环境、日志与失败演练

配置按环境注入，启动时检查必要配置是否存在；日志不输出口令、完整令牌或敏感请求体。限制日志大小并建立轮转，避免“程序正常、磁盘满了”。

可在隔离练习环境验证：应用启动失败、代理连不上上游、数据库短暂不可用、发布中断、回滚后读取新数据。记录现象、定位依据和恢复步骤；只有真的运行过才能写“已验证”。
