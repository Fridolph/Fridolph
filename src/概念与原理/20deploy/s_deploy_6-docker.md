# Docker 与部署边界

## 镜像、容器、网络与卷

镜像是应用运行所需文件和元数据的只读模板，容器是镜像的运行实例；容器共享宿主机内核，不等于完整虚拟机。端口映射决定外部入口，容器中的 `localhost` 只代表该容器自身。数据库容器可以通过服务名互联，不应为了方便把数据库端口直接暴露到公网。

可写层随容器删除可能消失；数据库数据需要持久卷和独立备份。卷解决持久化，不能替代备份，也不能直接把运行中数据库目录的文件复制当成一致性备份。

## 设计一份镜像时检查什么？

| 层面 | 学习重点 |
| --- | --- |
| 构建 | 多阶段构建，构建依赖与运行依赖分开，锁文件保证可重复安装 |
| 内容 | `.dockerignore` 排除本地缓存、Git 目录、环境文件和密钥 |
| 运行 | 非 root 用户、明确工作目录和资源限制 |
| 启动 | exec 形式如 `CMD ["node", "dist/main.js"]`，让进程接收退出信号 |
| 版本 | 固定可追踪版本；对可变 tag 的更新有策略，必要时固定 digest |
| 配置 | 运行时注入配置，不能将密钥写入镜像层或构建日志 |
| 退出 | 排空与清理时间应小于平台终止窗口 |

Node 作为容器主进程还要考虑子进程回收；存在多进程需求时评估 init 进程，而不是习惯性加 PM2。容器健康检查能报告状态，具体是否重启、摘流由运行平台决定。

## Compose 不等于生产治理

Compose 适合描述本地 API + PostgreSQL 等服务依赖。容器启动顺序不代表数据库已经可接入；即使有健康条件，应用也需要有限重试和故障恢复。数据库迁移建议作为受控的一次性发布步骤，不让所有副本同时抢着执行。

镜像回滚与数据库回滚仍是两件事。先学习单机部署与故障恢复，再根据负载和团队能力引入编排平台。
