# NestJS 服务设计：从需求到接口的最小闭环

> 状态：设计练习，尚未运行验证。本文把零散课程笔记串成一个可逐步实现的方案，不代表 [AI-Journey-land](https://github.com/Fridolph/AI-Journey-land) 已实现这些功能，也不会在本站安装 NestJS 或连接数据库。

## 先明确要解决的问题

学习过程中，笔记、代码和复盘经常分散在不同地方。第一阶段可以先解决“登录后保存、查看和修改自己的学习笔记”，让一次学习记录能持续积累。

动手前先写清：用户是谁，最痛的具体问题是什么，完成哪一步才算获得价值，用什么现象判断完成。框架、Redis、AI 都应服务这个目标。

**本轮闭环**：注册 / 登录 → 创建笔记 → 读取和分页查看自己的笔记 → 修改 / 删除 → 验证重启后数据仍存在。

暂缓后台菜单、多租户、微服务、RAG 和 Agent。Redis 也先按实际需求决定，避免为了“技术栈完整”增加尚未需要的基础设施。

## 从业务规则得到模块与技术方案

| 部分 | 首轮职责 | 边界与选择依据 |
| --- | --- | --- |
| UsersModule | 用户资料、账号持久化 | 密码使用合适算法哈希，响应不返回密码哈希 |
| AuthModule | 登录、身份验证 | 区分认证“你是谁”和授权“你能做什么” |
| NotesModule | 个人笔记 CRUD | 归属与修改规则放在业务用例中，不仅依赖前端隐藏按钮 |
| 数据访问 | PostgreSQL + 一种 ORM | 跟课可选 TypeORM；也可用 Prisma，首轮不同时维护两套 |
| 配置与日志 | 配置校验、requestId、错误记录 | 通用机制集中接入，避免每个 Service 重复读取配置 |

NestJS + TypeScript 有助于衔接前端经验，Module 与 DI 便于组织和测试。PostgreSQL 用来学习关系约束与并发控制；更详细的选型见[PostgreSQL 与 MySQL 对比](/学习自测/19database/q_database_1-postgresql_vs_mysql)。这些是选择理由，不意味着其他技术不能实现。

RBAC 角色权限、后台菜单、操作审计可以在业务需要时逐步加入。菜单是展示配置，不能代替服务端接口和资源权限检查。Redis 可用于共享会话、令牌撤销或缓存，但 JWT 验签本身不必每次访问 Redis；如果要求即时下线，就需要额外的会话 / 令牌状态策略。

## 先写接口契约，再实现链路

| 接口 | 输入要点 | 预期结果与边界 |
| --- | --- | --- |
| `POST /auth/register` | 邮箱、密码等 | 成功 201；重复账号按已定义的业务错误处理；并发重复由唯一约束兜底 |
| `POST /auth/login` | 登录凭据 | 成功 200；无效凭据 401；避免通过错误细节枚举账号 |
| `POST /notes` | 标题、内容 | 成功 201；归属取自认证上下文，不接受客户端指定其他用户 |
| `GET /notes` | 分页、可选关键词 | 成功 200；只查本人数据，限制分页大小并使用稳定排序 |
| `GET /notes/:id` | 笔记 ID | 成功 200；不存在或无权查看时，可统一 404，减少资源信息泄露 |
| `PATCH /notes/:id` | 允许修改的字段、预期版本 | 成功 200；本人笔记版本冲突 409；不存在或无权操作按既定策略返回 |
| `DELETE /notes/:id` | 笔记 ID | 成功 204、无响应体；是否支持并发删除保护需明确 |

输入格式错误通常返回 400，缺少或无效身份返回 401，已认证但权限不足通常是 403；也可以按资源隐藏策略返回 404，关键是策略一致。Nest 的 POST 默认是 201，登录等需要 200 的路由应显式配置 `@HttpCode(200)`；删除返回 204 也应明确设置。

PATCH 的 DTO 应区分“未提供”“空字符串”和 `null`，不要把可选字段理解成允许清空所有内容；空更新也应提前定义为拒绝还是无操作。错误契约可以包含 `code`、可公开的 `message` 与 `requestId`，不向客户端泄露 SQL、堆栈或密钥。

## 沿一次保存请求放置职责

```text
Middleware：生成或校验 requestId
  → Guard：校验身份，把可信 userId 放入上下文
  → Interceptor（进入）：开始观测本次处理
  → Pipe：校验 ID、DTO 与版本号
  → Controller：把 userId、id、dto 交给 Service
  → Service：检查规则，协调更新与事务
  → Repository：执行带归属和版本条件的更新
  → Interceptor（返回）：结果转换、记录处理耗时
  → 响应；未处理的异常走异常过滤器分支
```

Guard 执行早于参数 Pipe，不能直接假定其中的 ID 或请求体已经被管道转换、校验。依赖业务数据的归属检查可以放在 Service，并将归属条件落实到数据库操作里。

通用入口、业务规则和持久化的进一步区分见[MVC、DTO 与 DAO](/概念与原理/18nestjs/s_nestjs_11-layering_dto_dao)。

## 数据约束和并发设计要一起考虑

第一版可以从两张表开始，具体迁移在练习仓库中再实现：

| 表 | 建议字段与约束 | 对应业务意义 |
| --- | --- | --- |
| users | 主键、规范化邮箱的唯一约束、password_hash | 账号不可重复，不能存明文密码 |
| notes | 主键、owner_id 外键、title、content、version、时间戳 | 记录归属、内容与并发版本 |

标题长度、版本号非负等约束可以在适当层次表达。笔记列表按实际过滤与排序评估 `(owner_id, created_at, id)` 等组合索引，并用执行计划验证；PostgreSQL 不会因为声明了外键就自动为引用列建立索引。用户删除时限制还是级联删除笔记，也要先明确产品规则。

固定结构先使用普通列。后续出现可变的学习模块再考虑 JSONB，不要因为支持 JSON 就把所有字段放在同一个 JSON 对象里。

### 防止两个客户端互相覆盖

仅把“读取 → 修改”放进事务，不一定阻止丢失更新。可以让客户端提交预期版本，在一次 SQL 中完成判断、写入和版本递增：

```sql
-- 设计示意：$1～$5 必须通过数据库驱动绑定，不拼接用户输入。
-- 此处假设标题和内容已在业务层补齐；实际 PATCH 需保留未提交的字段。
UPDATE notes
SET title = $1,
    content = $2,
    version = version + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE id = $3
  AND owner_id = $4
  AND version = $5
RETURNING id, title, content, version, updated_at;
```

影响零行可能代表不存在、无权操作或版本冲突，不能一概解释为冲突。若需要区分，可按相同归属条件补查并依照契约映射，不能泄露他人笔记是否存在；需要更严格的一致性时，应在合适事务边界内设计锁与判断。客户端遇到 409 应重新获取数据、提示合并或确认覆盖，而不是无脑自动重放旧内容。

单条更新本身具有原子性。若保存笔记和写业务审计记录要求共同成功，就需要共享事务；缓存与消息不在同一个数据库事务内时，则要另行设计失效与可靠投递，不能靠一个数据库事务自动保证。

## 把开发、运维与安全问题变成可检查的约束

| 方面 | 首轮应落实的事情 | 容易忽略的边界 |
| --- | --- | --- |
| 多环境配置 | 开发 / 测试 / 生产隔离；启动时校验必要配置 | 不把密钥提交到仓库，不在日志输出连接串；测试不连生产库 |
| 数据访问安全 | 参数化查询、最小数据库权限、限制输入体积 | ORM 不能使原始 SQL 拼接自动安全，白名单也不能代替资源授权 |
| 认证与浏览器 | HTTPS；明确令牌存储、有效期与撤销方式 | Cookie 会话要考虑 CSRF；CORS 不是认证，也不阻止所有非浏览器调用 |
| 日志与审计 | requestId、状态码、耗时、必要错误上下文 | 过滤 Authorization、密码、敏感笔记内容；访问日志不等于业务审计 |
| 性能与可用性 | 分页、索引、连接池上限、外部调用超时 | 先观察慢查询、P95 / P99、错误率；限流与缓存按瓶颈加入 |
| 迁移与发布 | 审核迁移与兼容窗口，准备备份和恢复流程 | 生产不靠 `synchronize: true` 自动改表；回滚代码不等于回滚数据 |
| 下线与故障 | 停止接入新工作、有界等待、释放连接与后台任务 | 数据库断线和正常停机不同；写入结果不确定时不能盲目重试 |

具体关闭顺序和断线处理继续阅读[应用生命周期与数据库清理](/学习自测/18nestjs/q_nestjs_6-app_lifecycle)。这里描述需要考虑的设计，不修改本站部署、环境变量或数据库配置。

## 分成三个可以验收的切片

| 切片 | 要完成什么 | 应留下的证据 |
| --- | --- | --- |
| 1. 跑通契约 | Controller + DTO + Service + 内存仓储；身份可在测试中模拟 | 有效输入成功、非法输入 400、额外字段拒绝、响应字段明确；不把模拟身份版本对外发布 |
| 2. 建立真实闭环 | 接入账号认证、PostgreSQL、迁移与笔记 CRUD | 重启后数据存在、他人无法访问、重复账号受约束、列表只包含本人数据 |
| 3. 验证真实边界 | 并发修改、依赖故障与正常下线 | 同版本并发仅一次更新成功、失败无部分写入、错误不泄密、资源按预期释放 |

测试不要只验证“方法被调用”：纯规则写单元测试，Service 用替身验证业务分支；仓储与约束用独立 PostgreSQL 测试库做集成测试；E2E 覆盖 HTTP 状态、响应、身份与数据库结果。

至少验证：没有凭据的请求不能访问私有笔记，用户 A 不能操作用户 B 的记录，非法字段不能修改归属，两个同版本保存不能互相覆盖。数据库不可用时还要检查错误响应与日志，而不只是 happy path。

每个切片同步维护接口文档（如 Swagger / OpenAPI）、最小运行步骤、配置项说明和测试记录；涉及上线时再补充发布、回滚与恢复说明。实践完成后按[实践记录模板](/学习路线/实践记录模板)补上代码链接、命令和实际结果，再写入[博客](https://fridolph.github.io/fridolph-blog/)。

## 口述回顾

> 我会先确认用户问题与最小闭环，再拆模块和接口契约。Nest 中用 Controller 处理 HTTP 边界，DTO 和 Pipe 校验输入，Guard 处理身份与访问资格，Service 表达业务规则，Repository 访问数据库。同时把数据约束、并发更新、测试和错误响应设计进去。第一版先跑通可验证的闭环，再根据真实瓶颈加入 Redis、权限扩展或 AI 能力。

进阶时可以追问自己：为什么没有先加 Redis？怎样证明归属检查不会被绕过？一次更新结果未知时能不能重试？性能提升是靠指标证明，还是仅凭换了工具？
